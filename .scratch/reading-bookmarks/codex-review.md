结论：**澄清包需要修订后再进入实现。** 现有架构能够承载本地书签，但当前材料低估了扩展 PDF 续读的范围，也没有充分定义书签跳转、自动恢复和异步保存之间的协作。以下问题可以通过局部设计补齐，无须更换技术栈。

已只读核对指定 ADR、领域词汇及相关代码。`typecheck`、`lint` 均通过；执行时跳过会写入构建产物的前置脚本。未访问网络、未修改文件、未运行需要监听端口的测试。

### T1 web／服务端书签数据模型

- **推荐方案：** 在 `apps/server/src/schema.ts` 新建 `bookmarks` 表，包含独立主键 `id`、`book_id`、`chapter_position`、`block_position`、`created_at`；`book_id` 使用删除级联，位置建立 `UNIQUE(book_id, chapter_position, block_position)`。命名字段等 P4 确认后再加。SQL 全部落在 `apps/server/src/book-store.ts`，并将新表加入 `apps/server/scripts/check-sql-locality.mjs` 的归属映射。数量限制使用显式常量；达到上限拒绝新增，不静默淘汰已有书签。
- **原因：** 自动阅读进度是每书一个、持续覆盖的状态，手动书签是用户显式保留的位置集合。复用 `reading_progress` 会把两种生命周期绑在一起；独立表同时支持单签和多签，去重约束也能处理重复点击和请求重试。
- **替代方案：** 如果 P4 最终选择单签，可对 `book_id` 建唯一约束。把书签存为 `reading_progress` 的 JSON 列虽然少一张表，但会失去逐条约束、独立删除及清晰的并发边界，不建议。
- **潜在风险：** 书级外键不能证明目标块属于该书，新增时必须验证完整的“书→章→块”关系。去重、数量检查和插入应在同一事务内完成；已存在的同块书签应先返回，不能因为达到上限而拒绝一次幂等重试。
- **对 MVP 的影响：** 一张新表、几个 store 方法和迁移测试，工作量小。上限值、单签／多签属于待确认参数，不妨碍先明确独立存储的技术边界。

### T2 API、共享类型与错误口径

- **推荐方案：** 在 `apps/server/src/books-router.ts` 增加 `GET /:id/bookmarks`、`POST /:id/bookmarks`、`DELETE /:id/bookmarks/:bookmarkId`；新增请求使用 `{chapter, block}`。首次创建返回 `201`，同块重复请求返回已有书签 `200`，删除返回无正文的 `204`。在 `apps/server/src/wire.ts` 定义书签、位置及错误码类型，web 客户端落在新增的 `apps/web/src/bookmarks.ts`。存在且可读的书无书签时返回 `200 {bookmarks: []}`。
- **原因：** 集合资源与进度 upsert 必须分开。列表为空是正常结果，不能把缺书、读失败一律转换为空列表；现有 `fetchJson` 已支持 `204`，可以直接沿用。
- **替代方案：** 可以用位置组成 PUT／DELETE 地址，天然表达幂等，但独立书签主键更便于将来改名。只有 P4 选择命名后，才需要增加更新名称的接口。
- **潜在风险：** 建议明确错误矩阵：非法请求 `400`、书不存在 `404/book-not-found`、目标章块不存在 `404/bookmark-target-not-found`、书未就绪 `409/book-not-ready`、数量达限 `409/bookmark-limit-reached`；错误正文保留 `code + error`。删除必须同时限定书和书签主键，不能删除其他书的书签；可约定现存书下重复删除仍返回 `204`。不要直接复制进度 PUT 的整章加载来校验单块，新增轻量存在性查询即可。
- **对 MVP 的影响：** 三个接口足够覆盖不命名书签。服务端、web 客户端及真实契约测试须同票落地，避免只验证 router 而遗漏实际响应解析。

### T3 锚漂移与内容校验

- **推荐方案：** web 使用书内 `{章位置, 块位置}`，不做跨导入匹配；当前重新导入产生新书主键，原书内容不会因此被替换。扩展在 `apps/extension/src/store/library-store.ts` 增加内容版本标识，书签绑定版本；同标题导入但内容变化时，旧书签标记失效并禁止当作有效位置直接跳转。若需要迁移位置，再增加块原文校验。
- **原因：** web 与扩展的暴露面不同，不能统一估算。扩展的 `doc:${title}` 会原地替换内容，甚至可能合并两本仅标题相同的书；纯序数无法识别这种错配。前缀相同也不足以证明目标内容相同。
- **替代方案：** 为扩展保存块种类、完整原文摘要与邻近上下文，支持可靠校验；进一步做唯一匹配迁移属于更大的功能。更保守的方案是在内容变化后保留失效记录，但要求用户重新定位，避免模糊匹配。
- **潜在风险：** “就近块”只能保证位置合法，不能保证语义正确，不应静默宣称恢复成功。旧记录没有内容版本，升级不能伪造其与新内容一致；自动进度也要验证章块边界。现有扩展测试明确钉住了重导入保留进度，改变失效行为须作为显式行为变更更新测试。
- **对 MVP 的影响：** web 无须引入 CFI、字符偏移或搜索迁移。扩展若本期支持书签，至少要完成内容变化检测和失效处理，否则书签可能跳到完全不同的内容。

### T4 扩展端存储形状与写成本

- **推荐方案：** 在现有 `"library"` 记录增加按 `docId` 分组的书签集合，位置保留 `chapterIndex/blockIndex` 的零起点约定；统一由 `LibraryStore` 暴露增删列操作。在 `apps/extension/src/store/library-store.ts` 为旧记录补默认值，并同步更新内存实现和 Chrome 实现。一次操作用一次 `record.update` 完成校验、去重及写入。
- **原因：** 内容替换、版本变化、进度和书签可以在一个记录更新中保持一致；另开 namespace 会增加跨记录协调，而当前没有跨 namespace 事务。
- **替代方案：** 独立 namespace 可以降低书签操作时对书内容的重复读写，但需要处理书内容替换与书签更新之间的中间状态；适合确认存在性能瓶颈后再拆。
- **潜在风险：** [现有存储封装](/home/youyd/projects/claudeProjects/LinguaLeaf/apps/extension/src/store/namespace-record.ts:19)每次更新都读写整个 namespace，因此操作成本随整个书库增长，并非只随该书书签数量增长。队列也只属于一个封装实例，不能协调多个 store 实例或多个阅读标签页；入口聚焦旧标签页不是全局互斥。存储失败须向用户反馈，不能沿用当前进度写入的无捕获调用。
- **对 MVP 的影响：** 同 namespace 的增量最小，但旧数据兼容、失败提示和生产单写实例约束必须同时落实。批量处理应合并写入，不能逐签整库重写。

### T5 书签跳转、自动恢复与异步归属

- **推荐方案：** 让 `apps/web/src/progressSession.ts` 成为唯一的恢复与滚动协调者，由 `ReadingPage.tsx` 传入带操作标识的显式目标。跨章导航可携带块位置；同章再次跳转也必须触发新操作。优先级明确为“本次显式目标→自动进度→章首”，目标只在对应章内容 `ready` 后消费一次。读取及写入反馈使用 `useOwner.ts` 的属主令牌；书签创建时立即捕获书、章、块，避免响应时重新读取当前位置。
- **原因：** [当前恢复逻辑](/home/youyd/projects/claudeProjects/LinguaLeaf/apps/web/src/progressSession.ts:96)会在进度读取完成后主动滚动。在页面另加一个书签 `scrollIntoView`，会形成两个竞争的控制者；同章跳转还可能完全不触发现有 effect。
- **替代方案：** 独立书签跳转 hook 也可行，但必须通过明确接口暂停自动恢复和章首保存，协调成本更高。只增加 URL 参数而不调整会话逻辑不足以解决竞争。
- **潜在风险：** 250ms 只是程序滚动的保护窗口，不能保证晚到的进度响应不会再次覆盖目标，也不能保证用户在窗口内不会操作。属主令牌只阻止陈旧响应写 UI，不能撤销已发送的服务端保存；旧章 flush 与新目标保存必须有明确顺序。是否把跳转目标写成自动进度依赖 P8，但两个选项都必须禁止误写章首。目标失效时须提示并明确降级，不能静默成功。
- **对 MVP 的影响：** 这是实现中风险最高的部分，应先于入口 UI 完成。至少覆盖同章跳转、跨章跳转、连续点击、进度读取失败、晚响应和旧保存乱序；不要把正确性寄托在固定延时上。

### T6 进度外显的计算位置

- **推荐方案：** 若只显示章与块，直接使用现有 `BookSummary.progress`，落点是 `apps/web/src/BookshelfPage.tsx`，无需额外请求。若选择百分比，由 `apps/server/src/book-store.ts` 批量聚合计算分子、分母，在 `wire.ts` 定义结果；不要让书架逐书拉取正文。
- **原因：** 全书位置需要“此前各章块数＋当前章块位置”，只知道章号或当前章块数不够。服务端有完整数据，集中计算可以避免 N 次网络请求及正文解码。
- **替代方案：** 小书库先用集合聚合；性能证据表明不足后，再在导入事务里保存章块计数，并在 `schema.ts` 为旧书回填。冗余计数会增加维护不变量，当前不应默认引入。
- **潜在风险：** 数据库块还包括 `code/raw/image`，因此 `block_position` 不能直接称为“第 M 句”。必须定义百分比是位置比例还是完成度，是否计入非句子块，以及空章、无进度、总块数为零的结果；到达最后一块也不等于已读完。书架导入轮询会反复执行查询，应避免每书独立全表扫描。
- **对 MVP 的影响：** 更细位置文案成本小；准确百分比是中等增量，必须附带明确口径。两者不应混成同一项“显示优化”估算。

### T7 扩展 PDF 模式进度，仅当 P3 选择补齐

- **推荐方案：** 先把“记住页码”与“关闭后直接重开书”拆成两个验收目标。若只要求重新选择同一 PDF 后恢复，可在 `"library"` 增加按内容指纹索引的 PDF 进度记录；采用 `{kind: "pdf", pageIndex}`，内部零起点，在 `ReaderPage.tsx`／`pdf.ts` 调用边界转换为当前 PDF 的一起点页码。重流式进度保留独立形状，不将页码塞进 `ChapterProgress.blockIndex`。
- **原因：** [当前 PDF 分支](/home/youyd/projects/claudeProjects/LinguaLeaf/apps/extension/src/reader/ReaderPage.tsx:253)直接创建内存 `PdfSession`，随后返回，不调用 `saveDocument`；书库的 `ExtBook` 也只描述章节与块。新增页码字段本身无法让书重新打开。
- **替代方案：** 如果要求从最近列表直接重开，必须另行设计 PDF 文件持久化、书库条目类型和配额管理。当前硬约束限定状态使用 `chrome.storage.local`，不能未经决策直接引入 IndexedDB 或新的文件权限。
- **潜在风险：** 标题不足以标识 PDF；指纹应在交给解析器前计算。恢复时需校验整数、页数和范围，保存失败应可见。持久化 PDF 字节还会放大整个 `"library"` 的读写成本；文件重开、解析失败和会话释放也要覆盖。
- **对 MVP 的影响：** “重新选文件后恢复页码”是中等增量；“最近列表直接续读 PDF”明显更大。当前 brief 未区分这两种承诺，是估算缺口，不能按一个字段计价。

### T8 时间列与已记账卫生项

- **推荐方案：** 保留 `reading_progress.updated_at`；P2 若选择最近阅读，再由 `book-store.ts` 的书架查询读取它，并在 `wire.ts` 明确含义。对本次会触及的进度会话，修复 `saveFailed` 随属主变化的归属问题，同时用属主令牌过滤旧请求的成功／失败反馈；`Number.isInteger` 守卫按原待办补行为刻画测试，独立提交。
- **原因：** 写而未读不足以构成删列理由，该列可支持最近保存顺序。仅在切书时清零 `saveFailed` 不够：[旧请求回调仍会直接修改它](/home/youyd/projects/claudeProjects/LinguaLeaf/apps/web/src/progressSession.ts:73)，可能再次污染新书。
- **替代方案：** 卫生项可独立开票，但如果本期重做 T5，会话相关修复适合同批验证、分提交审查。仅展示细粒度位置而不做最近排序时，可以继续不对外暴露时间列。
- **潜在风险：** `updated_at` 是最后保存时间，不是最后打开时间；恢复已有位置后不滚动，未必触发新保存。排序必须定义空值及同时间的稳定次序，不能把“最近打开”和“最近保存”混用。守卫强化属于行为变更，不能混在行为零变化的重构里。
- **对 MVP 的影响：** 不删列几乎无成本；错误反馈归属修复是小而必要的增量。真正的最近打开语义需要额外事件，不能由现有列直接承诺。

### T9 测试与验收落点

- **推荐方案：** 服务端扩展 `apps/server/test/schema.test.ts`、`book-store.test.ts`、`api.test.ts`，分别覆盖旧库升级／重复启动、去重与级联／上限、HTTP 错误矩阵；新增 web 客户端调用时同步扩展 `apps/server/test/contract.test.ts`。web 在 `progressSession.test.tsx`、`reading.test.tsx` 验证跳转优先级和失败归属；扩展在 `libraryStore.test.ts`、`readerPage.test.tsx` 验证旧记录、内容替换、队列及恢复。
- **原因：** 仓库已有明确分工：store 验证持久化不变量，HTTP 验证接口，真实契约验证客户端解析，jsdom 验证状态机。仅使用内存扩展 store 无法证明 Chrome 旧记录升级和整记录写入行为。
- **替代方案：** 普通书签 CRUD 无须新增 local-e2e 驱动；涉及真实进程重启的新增承诺，再按 `docs/agents/local-e2e.md` 增加验证。真实滚动、浏览器历史、关闭重开、PDF 和扩展配额交给 `docs/agents/browser-e2e.md` 的浏览器／真机验收。
- **潜在风险：** jsdom 的几何和 `scrollIntoView` 桩不能证明真实可见位置；程序滚动保护窗口也不能只靠假计时器验收。扩展 Chrome stub 不能证明真实配额、标签页生命周期及权限。契约断言应锁状态、正文存在性和机器码，避免锁文案。
- **对 MVP 的影响：** 需要少量真实浏览器验收，不能全部留给组件测试。本轮只读检查已通过；完整测试套件及浏览器验收留给调用方执行，不将沙箱 `listen EPERM` 当作产品故障。

### P1 诉求确认

(a) 主要是发现性和文案，工作量小；(b) 必须先区分 web、扩展重流式和 PDF，并复现具体丢失路径，成本取决于故障位置。(c) 涉及持久化、接口、管理与跳转状态机，是完整功能增量，新增书签不能替代自动进度故障修复。

### P2 书架续读外显

(a) 无新增开发；(b) 显示章／块成本小，百分比需要新增统计口径；(c) 显式按钮可复用现有续读链接，成本小。(d) 最近保存排序成本较低，但最近打开需要新事件；独立区块还增加筛选、数量与空状态规则。

### P3 扩展 PDF 进度缺口

不补没有新增成本；补齐时，“再次选文件恢复页码”为中等工作量，“最近列表直接重开”为更大工作量。约束在于当前 PDF 不入书库、字节不持久化，而非页码字段缺失。

### P4 书签数量与命名

单签减少列表管理，多签增加逐项操作和上限处理；两者都可以使用独立书签表。命名进一步增加编辑入口、长度／空值校验及更新接口，成本主要在交互与契约，不在存储空间。

### P5 打点／管理入口

阅读页顶栏或目录面板能访问当前章块，成本较低，目录方案另需避免面板改变视口后再取位置。书卡适合管理已有书签；若允许在那里“打点”，必须先定义使用自动进度还是其他位置，书架当前没有实时阅读位置。

### P6 两端范围

web 先行工作量最小；两端各自本地需要两套存储适配、交互和验收，无法仅靠共享类型完成。跨端同步还缺稳定书身份、冲突规则和传输通道，且受本期不同步及 ADR-0006 无服务架构限制，不能作为顺带选项估算。

### P7 常驻“从头开始”

导航入口本身成本小，但必须通过 T5 的显式目标跳过自动恢复，否则第一章可能仍恢复到旧块。若还意味着清除进度，需要额外删除／重置语义；书签是否保留也须分别定义。

### P8 手动书签与自动进度的关系

并存可沿用独立集合与自动进度，成本较低，但仍需说明“访问书签后是否正常更新自动进度”。若书签持续覆盖续读目标，则增加默认目标来源、删除后的回退及优先级状态，明显高于一次跳转，不能只复用某条书签位置。

### 五维体检

| 维度 | 非空发现 |
|---|---|
| 内部一致性 | 位置序数覆盖多种块，不能直接称“第 M 句”；两端起点不同；“书签覆盖续读”尚未区分一次导航和持续默认目标。 |
| 完整性 | 缺少旧扩展记录升级、失效书签、空章、重复删除、配额失败，以及关闭页面时尚未完成保存的验收语义。 |
| 可行性 | PDF 续读被低估；扩展整库读写成本随书库增长；实例内队列不提供跨标签页互斥。 |
| 歧义 | “最近阅读”、百分比、“当前阅读位置”和“从头开始”均存在影响实现的不同解释，不能留给实现者临场决定。 |
| 风险与顺序 | 应先确定位置与失效契约，再实现持久化／API，再完成统一跳转会话，最后接入口；两端同做时，扩展内容身份应先于保留书签。 |

### 你发现被漏掉的技术题 / 与现状或 ADR 的冲突

1. **打点捕获规则没有单独定义。** web 使用首个仍露出视口的块，扩展使用顶部不超过 96px 的最后一个块，两端并不等价。需要分别明确空章、页尾、面板打开及键盘操作时的位置；无目标时禁用打点，不虚构块 1。落点：两端阅读页及 `readingProgress.ts`。

2. **“所有异步写已守属主令牌”不是现状。** `progressSession.ts` 的读取使用局部取消标记，保存反馈没有属主裁决。该项是新增实现必须落实的约束，不能当作现成保障。

3. **保存顺序与响应归属是两道题。** 同书切章时，旧保存晚到仍可能覆盖新位置；过滤陈旧 UI 响应不能解决数据库顺序。需要定义单页写入顺序，并说明多标签页／多设备竞争的边界；若只承诺最后到达者生效，也应写入验收条件。

4. **扩展内容身份需要显式处理。** 标题相同不代表同一本书；当前重导入后进入章首，而 store 保留旧进度，随后滚动又可能覆盖它。书签方案必须说明内容替换后的状态，不能仅增加一个数组。

5. **ADR 边界应准确表述。** CFI／原始 EPUB 定位不是当前模型的直接适配方案，涉及 ADR-0001 的重新评估；扩展 PDF 原位模式已存在，不能把 web 的重流式限制推广为扩展 PDF 无页坐标。通过 LinguaLeaf 服务实现扩展同步则需要重新评估 ADR-0006。

6. **标注书文件是否携带书签需要明确排除或立项。** ADR-0003 规定自包含 HTML，但没有赋予它应用进度的存取能力。本期若要求从导出文件恢复应用书签，会新增身份映射及数据交换，不能隐含在“导出”里。

7. **v1 spec 不能作为当前接口的唯一事实源。** 它仍记载 `PATCH /progress`、导入生成译文及多项已过时范围；实际代码使用 PUT，翻译时机由 ADR-0004 更新。新票应引用当前代码与后续 ADR，并补充“阅读进度／书签”的领域词条。

**Overall Verdict**: **NEEDS REVISION**。需要修订的是技术契约与估算边界；P1–P8 保持待产品决策，本身不构成架构不可构建。

**Top 3 Risks**（按影响排序）：

1. 书签跳转与自动恢复、章首保存、旧保存请求竞争，导致跳错位置或覆盖续读位置。
2. 扩展以标题覆盖内容且保留位置，缺少版本与失效机制，可能把书签指向另一段内容乃至另一本书。
3. 把 PDF 续读估成新增页码字段，遗漏文件身份、重开能力和存储成本，导致交付范围与实际能力不符。
