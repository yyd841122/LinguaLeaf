## 问题

`apps/web/src/taskFollower.ts` 的 tick `.catch` 只看 effect 级 `cancelled`,
不看 `ticket.stale()`:一个已被 `invalidate()` 作废的在途 tick(其成功响应
本会被丢弃)若随后失败,仍会把 `outage` 置真,页面上出现一个属于已作废轮次
的断连提示。

triage 复现实锤(2026-10-28,临时 repro 测试跑过即删):invalidate 后在途
tick reject → outage 置 true,下一鲜 tick 落地才清。可观测窗只在 shelf:
BookshelfPage 的 upload/delete 是唯二的 invalidate 调用点,提示渲染门控
serverUnreachable && hasImporting——症状为 mutation 刚成功后凭空出现一个
假「服务端不可达」提示,最多持续一个 interval。chapterTranslation 的轮询
不调 invalidate(route 变化/settle 走 effect teardown 的 cancelled,成功
失败两支都已被挡),翻译侧无可观测窗。

## 决策(锁定)

1. **作废轮次的失败不算服务端不可达**:catch 侧加 `ticket.stale()` 守卫,
   与 then 支对称——同一张票,成功被丢弃,失败同样不得发言。依据:GLOSSARY
   属主令牌字面(「响应落回时凭令牌裁决……丢弃响应、不写状态」,置 outage
   就是写状态);代价不对称——真断连最多晚一个 interval 被下一鲜 tick 认账,
   假提示则是 mutation 刚成功(server 明摆着可达)后凭空亮起。
2. **规则落 module 层一处,不按 mutation 类型分叉**:票面第二问(shelf
   upload/delete 与翻译 trigger 语义是否有别)在现状代码里消解——翻译轮询
   不产 stale 票,module 层一视同仁即可,零调用点改动。

## 回归测试(红验证)
